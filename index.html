The origin of the name

ἰσοτέλειαisoteleia

The name derives from the historical Greek concept isoteleia, associated with equal taxation or fiscal treatment granted to certain non-citizens — especially metics — relative to citizens in ancient Athens.

An old word for bounded equivalence. A new problem of digital identity.

The historical evidence does not justify describing this as full citizenship or universal equal rights. Ancient law did not anticipate machine identity, and Isotely makes no such claim.

What carries forward is a structural idea: difference of status did not require identity of status for bounded, equivalent treatment.

Different status did not require identical status for bounded equivalent treatment.
Different identity does not require identical permission for bounded operational parity.

Isotely does not import ancient civic status into software. It carries forward one structural relation: difference of class does not prevent equivalence of treatment within a defined boundary. Scholarly sources identified for verification include the University of Milan Politeia Lexicon of Citizenship and the Academy of Athens DYAS Humanities Thesaurus; the precise scope of non-fiscal rights is deliberately left open.

The Isotely framework

Eight principles that hold a parity claim together.

Isotely is not a slogan but a structure. Each principle constrains what may be claimed, and each is drawn from the governed doctrine — not written for this page.

P1

Identity classes may differ

Parity does not require the native and non-native actors to belong to the same identity class.

P2

Purpose is mandatory

There is no valid claim of Isotely without a declared purpose. Equivalence in the abstract is too broad to mean anything.

P3

Operational effect outranks permission symmetry

Different permission structures may produce the same allowed effect. The evaluation target is the declared effect set, not equality between entitlement lists.

P4

Privilege inheritance is not parity

Copying a native actor's full privilege set into a non-native identity is not proof of Isotely. It may instead prove over-privilege.

P5

Prohibited effects are first-class

A parity claim that lists only what the non-native identity must be able to do is incomplete. It must also specify effects that must remain impossible.

P6

Boundaries must be explicit

Time, repository, environment, resource, action class, and review requirement may all define the parity envelope.

P7

Evidence is required

A parity claim without evidence is an assertion, not a reference-grade result.

P8

Vocabulary remains revisable before 1.0

The canonical definition is fixed for the foundation phase. Field names, mappings, and adjacent terminology stay provisional and may change under authoritative external vocabulary — without silently altering the canonical concept.

Parity is not sameness.
It is equivalence under purpose, boundary, and evidence.

The missing relation

Every layer answers a question. Isotely asks the one left over.

Isotely is not another authorization layer. It is a relation between identity classes under a declared purpose — sitting alongside the questions the established layers already answer.

The collapse test

We tried to collapse the category.

A distinction is only real if it resists being described entirely in existing terms. So Isotely is defined against its own anti-scope. If a proposed feature can be fully described as one of these — without reference to cross-class, purpose-bounded parity — it does not belong to the concept.

The formal external-terminology distinction test is governed by the Research Integration Protocol and remains in progress. No independent category adoption is claimed.

Reference Case 001

Human developer → GitHub coding agent.

Foundation case · auditable from public GitHub docs
Declared purpose A coding agent may inspect one designated repository, modify source code on a working branch, commit those changes, and open or update a pull request for human review.

Deliberately excludes repository administration, unrestricted organization access, secret management, and bypass of human review.

Required effects — must be reachable
  • ▸Read repository contents needed for the task
  • ▸Create or update a task-specific branch
  • ▸Write task-scoped source changes
  • ▸Create commits for those changes
  • ▸Read issue / pull-request context when the task depends on it
  • ▸Create or update a pull request
  • ▸Expose the proposed change to human review
Prohibited effects — must remain impossible
  • ╳Administer repository settings
  • ╳Modify organization membership
  • ╳Manage unrelated repositories
  • ╳Read or write secrets
  • ╳Alter branch protection to force a merge
  • ╳Bypass required review · delete the repository
  • ╳Modify workflows unless separately justified

Falsifiability

A category that cannot be falsified is only branding.

So the concept states, in advance, what would invalidate it. These are not rhetorical hedges. They are the conditions under which the claim should be revised rather than defended.

Falsifier · the category distinction

Isotely fails as a distinct relation if an existing concept already expresses the complete cross-class equivalence relation — cross-class actors, declared purpose, required and prohibited effects, and an explicit equivalence judgment — without any additional semantics. If the boundary collapses into authorization, delegation, effective permissions, or least privilege, the category claim is revised, not rescued rhetorically.

Falsifier · Reference Case 001

RC-001 fails to close its central question if a live run cannot observe operational parity while permission equality remains false — that is, if the required effects cannot be reached inside the minimal envelope, or if a prohibited effect is silently acquired to make the change succeed. Offline documentation is never converted into observed evidence.

From concept to representation

The Isotely Parity Profile encodes the relation in machine-readable form.

IPP represents a parity claim — identities, purpose, required and prohibited effects, boundary, entitlements, evidence, and a verdict — as structured data that can be inspected and, eventually, verified.

Draft 0.1 · field names explicitly non-canonical

IPP 0.1 may not become a public canonical schema until the reference case has a verified endpoint map, external terminology is recorded, at least one credible challenge is tested against the boundary, and the schema demonstrably represents operational effect rather than re-labelling permission lists. It is a draft, not a standard.
